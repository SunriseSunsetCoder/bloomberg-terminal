## Capital deployment — frontier study (2026-08-09)

The "12 slots" was an unfinished attempt to answer *how to best deploy capital against this edge* — a portfolio-construction question, downstream of and separate from the (validated) per-trade edge. Ran it properly off `trades_t05_15yr.csv` (Q3–Q5, per-ticker non-overlap, compounding). **All figures FRICTIONLESS** → absolute CAGR is a ceiling; maxDD is an approx mark-to-market (linear interpolation of open-trade R) and **understates** true drawdown (true DD needs the daily per-ticker price paths, ~1,800 files, not pulled). Use it as a *relative map*, not a promise.

Sweep of concurrent slots × per-trade risk (15.6yr):

- **Signal capture is the binding constraint, not the edge.** Fires cluster, so a slot cap leaves most signals untaken: 6 slots → **21%** of Q3–Q5 captured, **12 → 37%**, 16 → 45%, unlimited → 100%. At 12 slots you skip ~63% of your own edge.
- **More slots → more return AND better return-per-drawdown** (diversification). At 0.5% risk: CAGR 33 / 44 / 55 / **66** / 83% for 6/8/10/12/16 slots; CAGR÷DD rises 6.0 → 11.5. Unlimited captures everything but needs ~36 concurrent positions on average (100+ in clusters) — operationally/liquidity-infeasible for small/microcaps.
- **Risk % is a near-linear return/drawdown dial.** 0.25 / 0.5 / 1.0% roughly scales both proportionally (12 slots: CAGR 29 / 66 / 167% at approx-MTM DD −3 / −7 / −13%).
- **Takeaway:** the ceiling on harvesting this edge is *how many concurrent (often small/micro-cap) positions you can realistically execute and manage*, not signal quality. Practical band ≈ 12–16 slots at 0.5–1% risk, matched to drawdown tolerance. Real costs + liquidity take a large bite on top (cf. the options Tier-1 finding: cost is the killer). Chart + full grid delivered to the user 2026-08-09.

**Lever test (2026-08-10)** — stacked four deployment improvements on a 12-slot baseline (day-batched fill engine; sector map = the compact 1,474-ticker `ticker_sectors.json`, 100% trade coverage; P-rank proxied by `hscore` since the trades CSV lacks the R:R half of the live blend). All FRICTIONLESS; DD approx-MTM (understated); read **CAGR÷DD (C/DD)** as the risk-adjusted verdict since conviction raises avg risk. NB the baseline here (43% CAGR / C/DD 5.5) differs from the frontier's 12-slot (66%) purely because this engine fills within-day by priority/alphabetical rather than shortest-first — compare *within* this test only.

- **Priority-fill by hscore** — take the best-scored setups first when a cluster exceeds slots. Lifts **taken-PF 2.69 → 3.07** (better trade selection); DD rises a touch so C/DD ~flat (5.5→5.2). Strictly better *quality*.
- **Liquidity filter (≥ $5)** — near-neutral in-sample (few sub-$5 in Q3–Q5), C/DD 5.2→5.7. Its real payoff is post-friction execution — keep it for real money, not for the backtest number.
- **Conviction sizing (Q3/Q4/Q5 risk = 0.35/0.55/0.85%)** — **the standout.** C/DD **5.7 → 9.6**, CAGR 48→72%, and DD actually *falls* (−8.4→−7.5%) despite ~10% higher avg risk. Pressing Q5 (PF 4.8) and easing Q3 (PF 2.0) is the single highest-value change — it's risk-adjusted, not just leverage.
- **Sector cap (max 3 open/sector)** — nearly free: CAGR 72→70%, DD flat, taken-PF up 3.61→3.81, and it adds correlation/tail protection the frictionless DD metric doesn't reward. Keep as cheap insurance.
- **FULL STACK @ 12 slots: 70% CAGR / −7.5% DD / C/DD 9.3 / taken-PF 3.81** vs baseline 43% / −7.9% / 5.5 / 2.69 — roughly **doubles risk-adjusted efficiency**, mostly from conviction sizing, with priority-fill + sector cap lifting trade quality (PF 2.69→3.81). @ 16 slots: 88% CAGR / −12.7% DD / C/DD 7.0 / 36% capture — more absolute return + capture, worse efficiency (an aggression dial). Chart delivered 2026-08-10.
- **Order of impact:** conviction sizing ≫ priority-fill (quality) > sector cap (insurance) ≈ liquidity (real-money only). Next real-world step would be true ADV-based liquidity + friction modeling, which the frictionless sim can't see.

**Recommended sizing (2026-08-10, from the tilt sweep).** Tier risk by handle-score quintile in a ratio of roughly **Q3 : Q4 : Q5 = 1 : 1.6 : 2.4**; pick the *level* for drawdown tolerance (the ratio drives risk-adjusted efficiency; the level just scales return + DD together). Two reference schemes: **Balanced / same-heat** — Q3 0.30% · Q4 0.50% · Q5 0.75% (avg ~0.5%); **Aggressive** — Q3 0.35% · Q4 0.55% · Q5 0.85% (avg ~0.6%, the C/DD 9.3 config). **Q5 HARD CAP = 1.0% risk/trade — never more** (above it the frictionless sim only looks better because it can't price single-name/microcap/gap risk). $350k dollar examples: Q3 ≈ $1,050–1,225 · Q4 ≈ $1,750–1,925 · Q5 ≈ $2,625–2,975 (Q5 ceiling $3,500). Risk ≠ position size: notional ≈ risk ÷ stop-distance (~10–13× the risk $), so **buying power, not risk, can become the binding cap on concurrent slots**. **Calculator:** `jack-sizing-calculator.html` on the dev box (`C:\Repos\bloomberg-terminal\`) + Cowork artifact `jack-sizing-calculator` — tier/entry/stop/account → shares, position, risk, caps + warnings enforced.

**Execution convention (confirmed in-parity with the backtest, 2026-08-10 — how Tee trades it).** Entry = next open after a daily CLOSE above the rim (EOD-confirmed). **Stop AND target are INTRADAY touches** placed as resting orders — target on `high ≥ target`, stop on `low ≤ stop`; **stop-first on a same-bar tie** (the backtest's conservative assumption; rare double-tag days can differ live). So realized exits track the 2.90 edge. NB the live JACK stop-hit *alert* is EOD/close-based — that's a backstop; the intraday resting stop is the real exit.

**Return analysis — $350k from inception, net of slippage + capacity (2026-08-10).** Full stack (12 slots · priority-fill · ≥$5 · sector-cap 3 · conviction 0.35/0.55/0.85%), Dec 2010 → Jul 2026 (15.6yr).

- **Capacity is the ceiling** — uncapped microcap compounding is impossible. 0.5% slippage + per-position notional cap: **$250k/pos → ~$12M (26% CAGR)** · **$1M/pos → ~$38M (35%)** · **$5M/pos → ~$124M (46%)**.
- **Realistic range: ~$12–40M / 25–35% CAGR** — pre-tax, assumes near-flawless execution of ~2,800 trades (realistically capture half-to-two-thirds). **Elite *small-account* compounder; CAGR decays with size as liquidity binds** → best on bounded capital / many small accounts, not one large pool. Realized-vs-paper is decided by **taxes** (high-turnover → short-term/ordinary income; where a trading-business structure earns its keep) and **execution discipline**, not the signal.
- **vs S&P 500 (same window):** SPY **+687% total / 14.2% CAGR / −33.7% maxDD**. Strategy beats it every year in the frictionless sim; realistically still market-beating after the capacity/tax/execution haircut.

## Trade selection — `priority` (P-rank)

`priority` = **50/50 blend of handle-score percentile rank + R:R percentile rank**. Validated best separator on full 15yr (separation +0.39, vs +0.36 R:R-only, +0.19 tier-only). Displayed as P1/P2/P3, not raw float.

**Source of `priority`:** read straight from the scanner CSV per row (`validation-core.ts` `getNum("priority","prio")`); NULL when the scanner didn't emit one. JACK does not compute it. A NULL priority → no P-rank chip and the row sinks in the sort. The scanner does not rank SKIP setups, so Q1/Q2 rows legitimately have no P-rank (confirmed by the 2026-08-08 diagnostic — see Resolved housekeeping).

**P-rank is now TWO independent sequences** (2026-08-08): LIVE rows ranked among themselves and PENDING rows ranked among themselves, each numbered from P1 (see the Board FIRED-status feature). A fired setup keeps its pending rank when it moves to the LIVE display group.

**R:R scale note:** JACK's `R_to_target` measures to the t05 **half**-target (median ~1.1), NOT the full target (~2.3). Pick-order R:R buckets are on that JACK display scale: <1.0 weak, 1.0–1.5 mid, 1.5+ strong.

**R:R-floor sweep — DONE 2026-08-15.** Ran on the re-exported `trades_t05_15yr.csv` (now carries `breakout`/`t05_target`), Q3–Q5 (7,660 trades, median R:R 1.17). **PF is flat ~2.7–3.2 across EVERY R:R band** — low-R:R trades just win more often (WR 85% in the <0.75 band), high-R:R trades pay more per win (+0.98R in the 2.0+ band). Raising a floor barely moves PF but bleeds total-R fast (none→4,301R; ≥1.0→3,271R/63% kept; ≥1.5→1,924R/30%). **So an R:R floor is a capacity/volume DIAL, not an edge filter — a hard cut removes profitable trades.** Corrects the earlier "maybe cut small-R:R" lean. Use **P-rank** for selection; keep any floor low. **Basket Sizer R:R-floor default = 0.75, editable (NOT 1.0)** — flag rows below it, don't hide by default. Chart delivered 2026-08-15.

## Exit / target (t05) — RE-EXAMINED, kept (2026-07-26)

Tested whether the t05 half-target is the best exit by re-simulating all **7,605 traded setups (Q3–Q5)** over the 15yr set under alternative exits (no-target, trailing 8/12/20%), scored **IS vs OOS**, plus per-trade MFE. **Verdict: t05 is the best risk-adjusted exit — kept.**

- Trailing/runner variants raise per-trade expectancy (no-target avgR ~1.0–1.2 vs t05 ~0.51–0.59) but **explode drawdown** (no-target maxDD −141 to −195R vs t05 −14 to −27R) and flip win rate **70% → 37–51%** (median trade becomes a full −1R loser). Higher expectancy, much worse ride.
- `trail_8%` is the only variant that beats t05 on PF **and** avgR in **both** IS and OOS (robust, not regime luck) — but at ~1.4–2.4× the drawdown, so **t05 still wins on return-per-unit-drawdown** (MAR ~160 vs ~130). Q5 is where a looser exit pays most (`trail_8` nearly clean on Q5 only).
- **Scale-out** (bank at t05 + run a slice) is the only untested structure that could beat t05, but is **bounded to marginal** by the trail results — a slice of an already-modest ~+11% expectancy gain — not worth changing a live, validated winner. A patch to add `t05_target`/`full_target`/`cup_depth`/`breakout` to the history notebook's trade output (needed to test it) is written and **parked**, not applied.
- Methodology note: the first MFE headline (median 3.17R) was **inflated** — MFE was measured over the full 120-bar window, counting post-stop-out rallies you could never capture. Corrected read = less capturable upside, which *reinforces* keeping t05.
- Data: `trades_t05_15yr.csv` (13,361 trades). The 13k is the **deliberately expanded universe**; the older cached 1,780 was the original smaller universe (per-year PFs consistent across the expansion → edge held). Colab notebooks in Drive `Bukowski`: `cup_handle_15yr_history*.ipynb` (builds the trades), analysis `cup_handle_t05_exit_rr_sweep_15yr_v2.ipynb`.

## Backtest fire/fill model (parity reference — from `cup_handle_15yr_history_1.ipynb`)

The exact model that produced the raw-R reference, confirmed by reading the notebook (Cell 3 detector + Cell 5 `_sim_trade`). Any live/paper replay MUST match this or the comparison is apples-to-oranges:

- **Fire** = the first bar with a **CLOSE strictly above the rim** (`C[j] > breakout`, breakout = `max(lch_high, rch_high)`), **within 15 bars after the handle low** (`range(h_idx+1, h_idx+1+15)`). Not an intraday touch, not an open-ended search.
- **Fill** = the **next day's OPEN** (`e_px = O[confirm+1]`). The trade file's `entry` column IS this realized open, NOT a buy-stop level. R is measured from it. (The scanner's own `entry` column is a different thing — a forward-looking buy-stop = rim + buffer — and must NOT be used as the fill.)
- **Exit** = **intraday-touch**: stop on `low <= stop`, target on `high >= target`, **stop checked first** (tie = stop-first), stop-outs are exactly **−1R**, timeout marks to the last close. Only the *entry* is close-confirmed; the *exit* is touch-based.
- **Time stop** = **120 bars** (`TIME_STOP_DAYS = 120`).

## Two-box deploy quick-ref (recurring gotchas)

Fuller infra is in the Bloomberg doc; this is the JACK-thread cheat sheet because the same friction recurs every deploy.

- **Boxes:** Win10 dev = `C:\Repos\bloomberg-terminal` (author + commit here; this is where Claude Code runs). VPS prod = `C:\Users\Administrator\Desktop\bloomberg-terminal` (runs the app via `npm run dev` Turbopack — **not** a prod build). The VPS is a **deploy mirror**: never author/commit/single-file-`checkout` on it. If it drifts (diverged / staged cruft), `git reset --hard origin/main` — `data/jack.db` and `.env.local` are gitignored, so they survive.
- **Push to main (a pre-push hook blocks main):** commit, then `$env:BYPASS_PUSH_PROTECTION="1"` **on its own line**, then `git push`. Committing straight to main is fine — only the *push* is gated. The feature-branch + merge dance failed mid-way repeatedly this session; **direct-to-main-with-bypass is the reliable path.**
- **Pre-commit hook needs `--no-verify` (confirmed 2026-08-07):** the husky **pre-commit** hook runs Biome via `pnpm`, which is NOT on the Win10 dev box PATH → the commit fails with `xargs: pnpm: No such file or directory` / `pre-commit script failed (code 127)` and **nothing gets committed**. The trap: a following `git push` then reports "Everything up-to-date" (a silent no-op — you think you deployed but didn't). Commit with **`git commit --no-verify`** (selftests are run manually before committing anyway). Note `BYPASS_PUSH_PROTECTION` covers only the *pre-push* hook, NOT this one — they're different hooks. Long-term fix: `npm i -g pnpm` on the dev box, or repoint the hook at `npx`. Always confirm a real deploy with `git log -1 --oneline` + a push that reports actual bytes.
- **CRLF silent patch failure (confirmed 2026-08-08):** this repo normalizes LF→CRLF (`git add` warns "LF will be replaced by CRLF"). Applying changes via a pasted diff/patch can **silently no-op** on the line-ending mismatch. Prefer direct edits (Claude Code editing the file) over pasted patches; if a change "didn't take," suspect CRLF first.
- **VPS `git pull` gc unlink prompt is harmless (confirmed 2026-08-08):** after a pull, git's auto-gc may prompt `Unlink of file '.git/objects/pack/pack-….idx' failed. Should I try again? (y/n)` — a Windows file lock (usually the running dev server holding a handle). The merge already completed (the `Updating X..Y Fast-forward` line above it is the truth). Answer `n`; optionally stop the dev server then `git gc` to tidy the stale pack. Not a corruption, not a failed pull.
- **Standalone scripts + env:** `npx tsx` does NOT auto-load `.env.local`. Scripts that hit Tiingo (recompute, rim-backfill) must run on the **VPS** (has `TIINGO_API_KEY`) or be passed `--env-file=.env.local`. DB migrations here are **dry-run-first, `--apply` to write**, and go direct-to-DB — never through `/api/jack-validation` (that spawns a run, becomes the board, and retires setups). Read-only diagnostics (`jack-priority-null-diagnostic.ts`, `jack-scorecard-inventory.ts`) are safe to run anytime on the VPS.
- **Deploy a code-only change:** Win10 commit+push → VPS `git pull` → restart `npm run dev`. No `npm install`/rebuild unless **dependencies** changed (dependency changes DO need `npm install` on both boxes first). **Additive DB migrations auto-apply** on the next `getDb()` (VPS restart) via `runMigrations`/`ensureColumns` in `lib/db/init.ts` — no manual DB step.
- **Alerts scheduler gating (`lib/jack/price-schedule.ts`, read 2026-08-07):** the whole scheduler tick early-returns on weekends + NYSE holidays (`if (!isTradingDay(now)) return`). Intraday monitor runs every ~30 min in market hours (09:30–16:00 ET); the EOD pass runs in an **18:00–18:15 ET** window (`EOD_SLOT` + `WINDOW_MINUTES=15`), once-per-ET-day via a Redis marker. So the close-confirmed entry burst only ever fires on a trading day at ~18:00 ET — never on a weekend.
